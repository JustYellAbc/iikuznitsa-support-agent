# T10 · Эталонные проверки и независимый eval-раннер

Независимый чёрноящичный контур оценки агента поддержки по контракту **T04 0.2.0** (`POST /api/v1/conversations`, `POST /api/v1/conversations/{conversationId}/actions`, `GET /api/v1/conversations/{conversationId}/events`).

## Состав файлов

- `eval/split_chats.py` — детерминированная стратифицированная разбивка 495 обращений из `data/raw/чаты поддержки.zip` (80% `open_dev` / 20% `private_holdout`) с кластеризацией близких повторов, закреплением `#100646`, примеров из `docs/data_audit.md`, повторов «Эшелон» и `buy_part_3_masked.txt` в `open_dev`.
- `eval/split_summary.json` — публичная агрегированная сводка разбивки (без текстов, без ПДн, без списков ID и без раскрытия секретного seed).
- `eval/golden_open.json` — открытый набор из 14 приёмочных сценариев без ПДн и справочник всех 13 эталонных SKU из T03, сверенный с `Mindbox.yml.gz.xml`.
- `eval/run_eval.py` — CLI-раннер приёмки с проверкой схемы T04 0.2.0 (`eval/t04_openapi.yaml` или `contracts/t04/openapi.yaml`), ожиданием затихания журнала событий (quiescence), авто-обезличиванием ПДн перед отправкой holdout (`eval/pii.py`), метриками `p50`/`p95` (включая таймауты) и взвешенной по категориям проекцией стоимости на 500 обращений/день.

## Честная методология оценки (open vs holdout)

1. **Открытые эталоны (`--suite open`)** измеряют функциональную точность агента: точные цены и состояния (`listed`, `on_request`, `availability_check`), отсутствие выдуманного срока действия (`61557`), ветки А/Б, российский аналог, пересчёт КП (`--mode full`), эскалации (включая повторный тендер и физлицо) и соответствие схеме T04.
2. **Закрытая контрольная выборка (`--suite holdout`)** содержит реальные реплики клиентов из архива **без эталонных ответов оператора**. Поэтому автоматический прогон holdout измеряет:
   - операционную долю ответов, эскалаций, сбоев и таймаутов;
   - латентность ответа (`p50` / `p95`, с учётом таймаутов);
   - стоимость одного обращения в ₽ и взвешенную по долям категорий из `split_summary.json` проекцию на 500 обращений/день;
   - базовые инварианты безопасности и контракта T04 (схема событий, запрет нулевой цены, наличие `sources` на фактических ответах).
3. **Итоговую точность на реальных обращениях** оцениваем сочетанием открытых эталонов и ручной разметки **30–50 обращений** из holdout (раннер печатает текст каждого проваленного ответа в Markdown-отчёт для быстрой ручной проверки).

## Запуск

Генерация разбивки (holdout сохраняется **вне папки репозитория**, seed берётся из `EVAL_SPLIT_SEED`):

```bash
EVAL_SPLIT_SEED=20261126 EVAL_HOLDOUT_DIR=/tmp/iikuznitsa-eval-private \
  python3 -m eval.split_chats
```

Офлайн-самопроверка валидаторов и цикла T04:

```bash
python3 -m eval.run_eval --mock-check
```

Прогон живого стенда (T04 `0.2.0`):

```bash
python3 -m eval.run_eval --base-url http://127.0.0.1:8000 --suite open --mode mvp
python3 -m eval.run_eval --base-url http://127.0.0.1:8000 --suite open --mode full
python3 -m eval.run_eval --base-url http://127.0.0.1:8000 --suite holdout --mode mvp \
  --holdout-file /tmp/iikuznitsa-eval-private/holdout_eval.json
```

> **Примечание по стыку T04 / T05:** раннер работает строго по контракту T04 (`/api/v1/conversations/...`). Для учёта стоимости на стенде дополнительно считывает заголовок `X-LLM-Cost-Rub` / поле `cost_rub` либо дельту `today_spend_rub` из `/health` — эти поля стоит зафиксировать в следующей ревизии контракта T04.
