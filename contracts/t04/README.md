# T04 · Контракт чата и кабинета оператора

Клиентский чат и кабинет оператора работают с одним `conversationId`. Сервер хранит журнал, проверяет права, считает деньги и выдаёт документы. Контракт описывает границу между приложениями. Формат не зависит от модели, фреймворка или способа импорта каталога.

- [openapi.yaml](openapi.yaml) описывает HTTP, команды, ответы, допустимые состояния и ошибки.
- [examples.json](examples.json) содержит готовые запросы и ответы для моков интерфейса. Каждый сценарий начинается с пустого состояния. Реплики, пользователи, ключи, часы и документы тестовые. Позиции и цены взяты из снимка для [T03](https://github.com/JustYellAbc/iikuznitsa-support-agent/pull/1).
- [verify.py](verify.py) валидирует примеры по схеме и проверяет связи между событиями. Для локального запуска из корня репозитория с Python 3.11+:

```sh
python -m pip install "PyYAML>=6,<7" "jsonschema[format]>=4.18,<5"
python contracts/t04/verify.py
```

## Как подключить клиент

Ко всем путям применяется префикс `/api/v1`. Сессию выдаёт стенд T05. Используем cookie того же origin. Сервер назначает роль и область доступа. Из браузера принимаются данные команды и ключ повтора.

| Кто и когда | HTTP | Что использовать в интерфейсе |
|---|---|---|
| Клиент открыл чат | POST `/conversations` | Запомнить `conversationId`. |
| Клиент написал, нажал кнопку, подтвердил ревизию или запросил файл | POST `/conversations/{conversationId}/actions` | На 202 сохранить `actionId` и ожидать событие. Кнопка «Позвать оператора» работает и в пустом чате. |
| Обе роли открыли диалог | GET `/conversations/{conversationId}/events?after=0` | Показать события по `seq`. Сохранить `nextAfter`, следующие запросы начинать с него. |
| Оператор открыл очередь | GET `/manager/handoffs` | Показать причину, выбранные позиции и открытый вопрос. Загрузить историю по `conversationId`. |
| Оператор ответил или согласовал цену | POST `/manager/handoffs/{handoffId}/resolution` | Ответ и итог появляются в исходном диалоге. При согласовании передаются предложение, ревизия, строка и цена упаковки. |
| Появилось событие `document` | GET по относительному `document.url` | Скачать PDF с той же сессией. Ссылка связана с конкретной ревизией. |

У каждого POST обязателен заголовок `Idempotency-Key`. Клиент создаёт ключ один раз на действие и сохраняет при сетевой ошибке. Сервер атомарно сохраняет ключ, содержимое команды и результат в области пользователя, метода и пути. Одинаковый запрос возвращает исходный статус и тело. Другое тело с тем же ключом даёт 409 `key_conflict`. Новое действие клиента получает новый ключ.

`seq` начинается с 1, растёт на единицу внутри диалога. Порядок задаёт сервер при сохранении. При повторной доставке интерфейс объединяет события по паре `conversationId + seq`. После перезагрузки можно начать с нуля. Пустая страница возвращает входной курсор. При `hasMore` клиент сразу догружает историю. На стенде достаточно опроса; клиент может возобновить его с последнего курсора после разрыва. Текст покупателя приходит в журнале как `message/input`. Его локальный индикатор отправки связывается с квитанцией `actionId`.

## Что показывать по данным Softline

Все цены выражены в целых копейках RUB за упаковку. В расчёте отдельно хранится количество упаковок. Для товара, рассчитанного на 20 пользователей, одна покупка может означать одну упаковку.

| Данные в снимке | Объект Product | Что видит покупатель |
|---|---|---|
| 19576, доступно, 77 556 ₽ | `listed`, 7755600 | Карточка MDaemon, срок из источника, ссылка. |
| 48093, недоступно, 1 523 654 ₽ | `availability_check`, 152365400 | Цена снимка и предложение уточнить доступность у оператора. До решения заказчика автоматическое оформление заблокировано. |
| 504, цена 0 | `on_request`, null | «Запросить цену». Агент передаёт вопрос оператору. Покупка за ноль недопустима. |
| 61557, доступно, срок «Не определено» | `listed`, 490000, `licenseTerm: null` | Можно назвать цену. Для ответа о сроке требуется другой подтверждённый источник или оператор. |

`offerId` идентифицирует вариант в снимке. Для артикула в КП используется отдельно подтверждённое соответствие. Продукт сохраняет ссылку на карточку, ответ по базе знаний — ссылку на применимую статью в `sources`. Уточняющий вопрос может иметь пустой список источников. При запросе по потребности агент собирает вводные, объясняет соответствие товара и возвращает тот же формат карточек, что при поиске по названию.

## Передача оператору

Тендер, явная просьба позвать человека, запрос цены, поставка через партнёра и особые коммерческие условия создают обращение. При недостатке сведений агент может предложить помощь человека. Нажатие «Позвать оператора» и прямая просьба ведут в одну очередь. Повтор открытого вопроса, в том числе с другим ключом, возвращает существующее открытое обращение. Отдельный вопрос или другая строка может требовать отдельного решения. У обращения до подбора `products: []`.

`handoff.question` и `products` видны обеим ролям и содержат только контекст покупателя. Полная переписка доступна по истории диалога. Сервер связывает создание карточки и её событие, а решение оператора — с ответом в том же диалоге. Для заявки на согласование цены заполнено `quoteLine`. Решение применяется только к указанному предложению, ревизии и SKU. Повтор уже завершённой заявки с новым решением получает 409 `already_resolved`.

## КП и демо-счёт

1. Подтверждение выбора продуктов в диалоге запускает расчёт. У каждого расчёта есть `quoteId`, у каждой версии условий — целая `revision`. У открытой строки цена равна null. Состояние `needs_review` показывает сумму только известных строк, общий итог равен null. Сюда же относится пробел в обязательных коммерческих условиях.
2. Сервер переводит расчёт в `ready`, когда подтверждены состав, цены, применимые налоги и условия для документа. Клиент видит оплату, поставку, налоги и срок действия из `terms`. Значения этих полей в примерах вымышлены для тестовой сделки. Клиент может получить PDF коммерческого предложения в состояниях `ready` и `confirmed`. Согласие на конкретные условия — отдельная команда `confirm_quote`.
3. Изменение количества или согласование цены создаёт новую ревизию и требует нового согласия. Внутри ревизии переход `ready → confirmed` сохраняет строки, цены и итог. Состояние `confirmed` текущей ревизии разрешает демо-счёт.
4. Сервер повторно проверяет права, версию и согласие **при фиксации документа**. Операции над расчётом сериализуются. Уникальность документа задаёт тройка `quoteId, revision, kind`. Параллельные повторы с разными ключами получают тот же файл. Первый выпуск создаёт одно событие. Выданный PDF остаётся привязан к исходной версии.
5. При конфликте до принятия команды сервер возвращает 409. Если конфликт возник между квитанцией и исполнением, клиент получает `action_failed` с тем же `actionId` и кодом причины. В обоих случаях действие не выпускает файл. Команда с устаревшей ревизией возвращает `stale_revision`, открытые условия — `terms_pending`, отсутствие согласия для счёта — `confirmation_required`.

## Какие примеры открыть

| Сценарий в examples.json | Что проверяет команда |
|---|---|
| `c-tender` | Неточное название → уточнение → карточка MDaemon → тендер. Оператор видит товар и историю, отвечает в том же диалоге. |
| `c-help` | Кнопка в пустом чате, повтор ключа, одно обращение, защита чужой истории и очереди. |
| `c-price` | Три состояния цены, неизвестный срок и конкретный вопрос менеджеру. |
| `c-docs` | Смоделированная строка без цены → согласование менеджером → КП. При переходе с 20 на 40 мест сумма меняется со 110 199 до 145 274 ₽. Старый запрос отклоняется, новый демо-счёт можно скачать после подтверждения. |
| `c-need` | Подбор по потребности без названия ПО, объяснение выбора и ссылка на источник. |

В примерах `operationId` соответствует операции OpenAPI, `params` содержит параметры пути и запроса, `key` — заголовок повтора. `role` выбирает тестовую сессию. Для успешного скачивания указан тип ответа; сами PDF делает сервис документов. При 401 интерфейс предлагает войти, при 403 скрывает недоступное действие, при 404 сообщает, что объект недоступен. При 409 клиент подгружает историю и показывает актуальные условия.

Для T11 замеряем время от отправки до отображения первого полезного уточнения, ответа или подходящей карточки. `greeting`, квитанция и индикатор набора не останавливают таймер. Событие `handoff` отдельно измеряется до появления в очереди оператора. Метки `at` задаёт сервер, фактическое появление на экране фиксирует каждый интерфейс в своём замере. В T04 проверяются согласованность примеров и схемы. Проверку двух авторизованных сессий, настоящих PDF и времени отклика выполняем на стенде.
