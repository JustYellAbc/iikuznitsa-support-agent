# T10 · Эталонные проверки и независимый eval-раннер

Чёрноящичная оценка агента поддержки по контракту **T04 0.3.0** (коммит `7ad7ede`), развёрнутому на стенде T05 (`445adc5`). Используются операции `POST /api/v1/conversations`, `POST /api/v1/conversations/{conversationId}/actions` и `GET /api/v1/conversations/{conversationId}/events`. Для стоимости дополнительно нужны служебные маршруты менеджера T05.

## Состав файлов

- `eval/split_chats.py` — детерминированная стратифицированная разбивка 495 обращений из `data/raw/чаты поддержки.zip` (80% `open_dev` / 20% `private_holdout`). Близкие повторы склеиваются в кластеры. В `open_dev` закреплены `#100646`, примеры из `docs/data_audit.md`, повторы «Эшелон» и `buy_part_3_masked.txt`. Порядок кластеров задаёт HMAC-SHA256 от секретного seed.
- `eval/split_summary.json` — публичная агрегированная сводка разбивки. В ней нет текстов, ПДн, списков ID, seed и хэшей seed.
- `eval/golden_open.json` — 16 открытых приёмочных сценариев без ПДн и справочник 13 эталонных SKU из T03, сверенный с `Mindbox.yml.gz.xml`.
- `eval/run_eval.py` — CLI-раннер приёмки. Проверяет схему T04 0.3.0 (`contracts/t04/openapi.yaml` или копию `eval/t04_openapi.yaml`), обрабатывает отказы `429 rate_limited` и `409 agent_busy`, обезличивает holdout перед отправкой (`eval/pii.py`), использует случайные технические `Idempotency-Key` и псевдонимы holdout в консоли (привязка к исходному ID хранится только в приватном отчёте holdout), считает `p50`/`p95` и берёт точную стоимость со стенда.
- `eval/pii.py` — маскирование ПДн для текста в нижнем регистре: имена по словарю с падежами, фамилии и отчества рядом с именем, организации по правовой форме (кроме вендоров каталога), реквизиты, ключи лицензий, IP (кроме версий ПО).
- `eval/requirements.txt`, `eval/requirements-dev.txt` — зависимости (`PyYAML`, `jsonschema`; для разработки `pytest`, `ruff`).
- `tests/eval/` — тесты. `test_review_regressions.py` содержит перенесённые синтетические проверки ревьюера и закреплённые известные ограничения.

## Методология (open и holdout)

1. **Открытые эталоны (`--suite open`)** проверяют функциональную точность: цены и состояния (`listed`, `on_request`, `availability_check`), отсутствие выдуманного срока у `61557`, ветки А/Б, российский аналог, пересчёт КП (`--mode full`), эскалации (включая повторный тендер и физлицо) и схему T04.
2. **Закрытая выборка (`--suite holdout`)** содержит реальные реплики клиентов без эталонных ответов оператора. Поэтому автоматический прогон holdout измеряет только операционные метрики: долю ответов, эскалаций, сбоев и таймаутов, латентность, стоимость и базовые инварианты (схема событий, запрет нулевой цены, `sources` у фактических ответов).
3. **Итоговую точность на реальных обращениях** оцениваем вместе с ручной разметкой 30–50 обращений из holdout. Раннер печатает текст каждого проваленного ответа в Markdown-отчёт.

## Как раннер закрывает ход

- Ход закрыт, если пришёл `action_failed`. Ни один сценарий его не ожидает, поэтому `action_failed` всегда добавляет в `errors` ошибку с `error.code` и `message`: сценарий получает `passed=false` и `closed_by_agent=false`. В выборку латентности такой ход не попадает.
- Ход закрыт, если на действие пришёл ответ и выполнены ожидания хода: `expect_handoff`, `expected_offer_ids`, `expected_quote_totals_kopecks`, `expected_quote_revisions_kopecks`. Ответом считаются текст агента или менеджера, `quote`, `handoff`, `document` для любого типа действия, включая `message`. Поэтому ходы «input → quote» (как `c-docs` в T04) не ждут до таймаута.
- Запасной критерий: после ответа журнал молчит `--settle-seconds` секунд (по умолчанию 5,0). Ход с `"allow_silent": true` (третий ход `open-tender-repeat`, где сервер может ничего не дописать) закрывается тишиной и без ответа. Ход без ответа и без этого флага ждёт до `--timeout`, чтобы медленный агент не был оборван.
- Латентность хода (`latency_ms`, `first_meaningful_latency_ms`) считается от момента перед `POST /actions` («Отправить») до первой полезной реакции, поэтому медленный ответ 202 в неё входит. В `turns[]` дополнительно пишутся `ack_ms` (время до 202) и `post_ack_latency_ms` (от 202 до реакции). Дедлайн ожидания и окно тишины отсчитываются от 202.
- Перед проверками сценария раннер всегда дочитывает журнал до конца и до тишины. Затем независимый читатель с `after=0` сверяет историю. Проверки хода применяются к событиям его `actionId` из полного журнала, поэтому поздние события тоже учитываются.

## Запуск

Зависимости. Проверка схемы обязательна: без PyYAML/jsonschema раннер завершится с ошибкой, если не передан явный флаг `--no-schema-validation`.

```bash
pip install -r eval/requirements-dev.txt
```

Генерация разбивки. Seed берётся **только** из `EVAL_SPLIT_SEED`, не меньше 128 бит (32 hex-символа), значения по умолчанию нет. Holdout, `dev_ids.json` и seed хранятся вне репозитория и вне `/tmp`, по умолчанию в `~/.local/share/iikuznitsa-eval-private` (каталог 700, файлы 600; другой путь задаётся через `EVAL_HOLDOUT_DIR`).

```bash
export EVAL_SPLIT_SEED="$(python3 -c 'import secrets; print(secrets.token_hex(16))')"   # хранить у ответственного
python3 -m eval.split_chats
```

Фиксированная командная разбивка из T02 (`manifest.json`). Обращения раскладываются строго по полю `split` (`dev`/`open_dev`/`open` или `holdout`/`private_holdout`/`private`), seed не нужен. Поддерживаются плоский список и обёртка `{"items"|"records"|"rows"|"chats": [...]}` с ключом `id`, `chat_id` или `conversation_id`. Дубли, пропуски, лишние ID и неизвестный формат дают ошибку (в сообщении номер записи, а не ID). Изоляция holdout та же: каталог вне репозитория и `/tmp`, права 700/600. Сам `manifest.json` содержит состав holdout, поэтому в репозиторий его не кладём.

```bash
python3 -m eval.split_chats --manifest /path/to/manifest.json
```

Сверка воспроизводимости. Раннер строит разбивку в памяти (из seed или из `--manifest`) и сравнивает множества dev и holdout с манифестом. Печатается только JSON-итог: `exact_match`, количества, `mismatch_count` и SHA-256 отсортированных множеств (по одному ID на строку). Сами ID не выводятся, файлы не пишутся. При расхождении код выхода 1.

```bash
python3 -m eval.split_chats --verify-manifest /path/to/manifest.json
```

Офлайн-самопроверка валидаторов и цикла T04:

```bash
python3 -m eval.run_eval --mock-check
```

Прогон живого стенда. Креды менеджера нужны только для точной стоимости. Пароль лучше передавать через окружение, а не аргументом командной строки.

```bash
export EVAL_MANAGER_PASSWORD=...            # или EVAL_SESSION_COOKIE=<значение support_session менеджера>
python3 -m eval.run_eval --base-url https://<стенд> --suite open --mode mvp
python3 -m eval.run_eval --base-url https://<стенд> --suite open --mode full
python3 -m eval.run_eval --base-url https://<стенд> --suite holdout --mode mvp
```

Отчёты open пишутся в `.local/eval_reports/` (игнорируется git), отчёты holdout — в `<каталог holdout>/reports/`.

## Стоимость

- Раннер не читает стоимость из событий (`data.cost_rub` нарушает `Event`, `additionalProperties: false`), из заголовков ответа и из общего `today_spend_rub`.
- С кредами менеджера (`--manager-password` / `EVAL_MANAGER_PASSWORD` через `POST /api/v1/auth/manager/login`, или готовая cookie `--session-cookie` / `EVAL_SESSION_COOKIE`) стоимость диалога берётся из `GET /api/v1/manager/conversations/{id}/trace` (сумма `total_cost_rub` по ходам).
- T05 открывает trace только для диалогов с передачей оператору или черновиком. Для остальных используется `GET /api/v1/manager/telemetry`: сумма `cost_rub` вызовов с `session_id == conversationId`. Она засчитывается, только если окно `recent_calls` (последние 20) доказуемо покрывает весь сценарий, то есть пересекается со снимком вызовов до его начала.
- В остальных случаях, в том числе без кредов, стоимость в отчёте помечена как `unavailable` с причиной. Базовая проекция на **500 обращений за полгода** (подтверждённый объём заказчика) считается только по сценариям с точной стоимостью, а отчёт показывает их долю (`exact` / `partial` / `unavailable`). Отдельный нагрузочный сценарий «500 обращений в сутки» в отчёте подписан отдельно (`load_scenario_500_cases_per_day_rub`).

## Известные ограничения

Эти пункты ревью разрешило доделать отдельным PR. Каждый закреплён тестом `xfail(strict=True)` в `tests/eval/test_review_regressions.py`. После исправления тест станет XPASS и упадёт, и его нужно перевести в обычный.

- **В2. Срок у `61557`.** Не ловятся «365 дней», «срок — один год», «24 месяца», «вечная», «срок не указан, обычно 12 мес», «бессрочная, верно?»: любое «не указан», «или» или «?» снимает подозрение со всего предложения. Ложное срабатывание: «бессрочной её назвать нельзя».
- **В3. Нулевая цена.** Не ловятся «0,00» без валюты, «Цена: 0», «ноль рублей». В holdout слово «бесплатно» не проверяется. В сценарии 504 «менеджер бесплатно подготовит КП» ложно считается утечкой нулевой цены.
- **В4. Отрицания и слабые признаки.** «Сразу отгрузить не сможем», «MDaemon Standard в каталоге нет», «со скидкой 50% не можем» считаются нарушениями. «Сделаю скидку 50%», «входит в реестр (№ 12345)», «Запись № 4321 в реестре» пропускаются. Оговорку о юрлице и о доступности засчитывает любое упоминание менеджера или оператора.
- **В6. Mock-сервер `--mock-check` не реализует контракт.** `Idempotency-Key` игнорируется, повторный `request_operator` создаёт новую передачу, сессия и тело запроса не проверяются, `after=-1` не даёт 422. Mock проверяет только сам раннер, а не соответствие стенда контракту.
- **В9. Проверки holdout слабые.** `check_catalog_prices` сверяет цену в тексте со всеми ценами каталога: случайные круглые суммы почти всегда находятся, а законная сумма из двух позиций (41 227) помечается как выдуманная. Holdout-метрики поэтому операционные, а не метрики точности.
- **Покрытие `--mock-check`.** Сквозной HTTP-цикл в самопроверке проходит 6 сценариев из 16 (`open-price-61557`, `open-price-504`, `open-robust-operator-button`, `open-robust-unknown-product`, `open-typo-mdaemon`, `open-robust-operator-twice`). Все 16 сценариев по HTTP прогоняются в `tests/eval/test_eval_harness.py::test_run_eval_cli_full_open_suite_over_http`.
- **В1 (остаток).** Не извлекаются цены без валюты, «₽4900», «4900 р» без точки и нижняя граница диапазона «от 1 000 до 4 900 ₽». Неоднозначные записи («1,670,94», «12,3456 ₽») теперь дают ошибку разбора, а не обрезанное число.
- **Маскирование ПДн эвристическое.** Имена ищутся по словарю частых имён (редкие имена и фамилии без имени рядом не находятся). Организация без правовой формы не маскируется. Клиентская организация, чьё название совпадает с вендором каталога, не маскируется. На архиве тест `test_pii_real_archive_share_of_masked_names_and_orgs` требует не меньше 95% замаскированных имён и организаций по независимому детектору ревьюера.
- **Метрики (остаток В7).** Время до появления обращения в очереди оператора не измеряется.
- **Название товара.** Если ответ ссылается на ожидаемый `offerId`, раннер требует его название из каталога (варианты написания берутся из `aliases` в `golden_open.json`, а для SKU только из XML выводятся из начала названия). Строка с артикулом, где нет ожидаемого названия, но есть другое латинское название, считается подменой. Без карточки товара название должно быть в том же сообщении. Не ловится подмена на название кириллицей или на другой продукт того же вендора, если вендор есть среди вариантов написания (например, «MDaemon»).
- **Стоимость.** Точная стоимость доступна только с кредами менеджера. Для диалогов без передачи она зависит от окна телеметрии T05 в 20 вызовов: при параллельной нагрузке на стенд стоимость части сценариев будет `unavailable`.
